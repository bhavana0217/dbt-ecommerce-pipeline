# dbt E-commerce Pipeline — Governed Analytics Engineering

**One-liner:** A dbt project that turns three messy raw extracts from a fictional
online retailer into two trusted, tested revenue marts — with data-quality
tests, a type-2 customer snapshot, and a post-build health monitor that fails
CI when the *data* looks wrong.

This is the analytics-engineering half of a modern data stack: raw → staging →
marts, every cleaning decision documented, every mart covered by tests, and
monitoring that watches the data itself, not just the job status.

## Business problem

A mid-size e-commerce company dumps daily extracts from its order system, CRM,
and product catalog. Leadership wants two things it can trust:

1. **Daily revenue** — what did we actually earn, every day, in USD?
2. **Customer lifetime value** — who are our best customers and how recently did they buy?

The raw extracts are messy in exactly the ways real ones are: duplicate events,
three timestamp formats, mixed currencies, duplicate CRM accounts, and prices
stored as `"$1,299.99"`. This pipeline makes the mess auditable instead of
invisible.

## Architecture

```
┌─────────────────────┐
│  generate_data.py   │  seeded generator → reproducible raw extracts
└─────────┬───────────┘
          │ CSVs
          ▼
┌─────────────────────┐
│   dbt seed (raw)    │  raw_orders · raw_customers · raw_products
└─────────┬───────────┘  (raw schema — never queried directly)
          ▼
┌─────────────────────┐
│  staging (views)    │  stg_orders · stg_customers · stg_products
│  clean + dedupe     │  one documented rule per mess (see below)
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│ intermediate (view) │  int_order_lines — the single clean grain:
└─────────┬───────────┘  one row per order line, enriched
          ▼
┌──────────────────────┐     ┌──────────────────────────────┐
│ marts (tables)       │     │ snapshots                    │
│ mart_daily_revenue   │     │ customers_snapshot (type-2   │
│ mart_customer_       │     │  history of customer attrs)  │
│   lifetime_value     │     │                              │
└─────────┬────────────┘     └──────────────────────────────┘
          ▼
┌─────────────────────┐
│ monitoring/         │  freshness · volume · null-rate checks
│ check_pipeline.py   │  → pipeline_health table, exits 1 on FAIL
└─────────────────────┘
```

## The data

Generated by `generate_data.py` (seed 42; window always ends yesterday so the
freshness check stays meaningful). Exact injected-issue counts are written to
`data_manifest.json` — every number below comes from there, not from memory.

| Raw table | Rows | Injected issues |
|---|---|---|
| `raw_orders` | 32,480 order lines (2025-01-21 → 2026-09-22) | 480 duplicate events, 310 negative quantities, 666 unparseable timestamps, 159 orphan lines (no customer), mixed USD/EUR/GBP casing |
| `raw_customers` | 5,092 accounts | 92 duplicate emails (unmerged CRM accounts), 389 missing emails (7.6%) |
| `raw_products` | 618 SKUs | 18 duplicate SKUs with drifted prices, 23 missing categories, ~15% of prices as `"$1,299.99"` |

### How each issue is handled (and why)

| Issue | Handling | Rationale |
|---|---|---|
| Duplicate order events | Dedupe on `order_line_id`, keep latest | A re-emitted event is never new information |
| 3 timestamp formats + garbage | `try_strptime` cascade; unparseable → dropped | A revenue mart must never silently misplace revenue in time |
| Negative quantities | Dropped | Data-entry errors — real returns are separate `refunded` rows |
| Mixed currencies | Upper-cased; converted with static illustrative FX rates (USD 1.0, EUR 1.08, GBP 1.27) | Production would join a daily FX table; static rates keep the demo reproducible |
| Duplicate customer emails | Merge on `lower(trim(email))`, earliest signup survives | First-seen record is the most defensible truth |
| Missing emails / countries / categories | Kept as NULL / `'Unknown'` / `'Uncategorized'` | Honest and BI-friendly; NULLs don't group well in dashboards |
| `"$1,299.99"` prices | `regexp_replace('[$,]')` → numeric | — |
| Orphan order lines | Kept, flagged `is_orphan_order` | Real revenue must not vanish; attribution limits are monitored, not hidden |

Net effect: **1,452 of 32,480 order lines (4.5%) rejected, 92 duplicate
customers merged, 18 duplicate SKUs resolved** — verified by `dbt build` output.

## Models

| Layer | Model | Grain | Materialization |
|---|---|---|---|
| staging | `stg_orders` | order line | view |
| staging | `stg_customers` | customer | view |
| staging | `stg_products` | product | view |
| intermediate | `int_order_lines` | order line (enriched) | view |
| marts | `mart_daily_revenue` | calendar day | table |
| marts | `mart_customer_lifetime_value` | customer | table |
| snapshot | `customers_snapshot` | customer version (type-2) | snapshot |

**Marts in numbers:** `mart_daily_revenue` holds 610 days and **$11,916,738.71**
total revenue; `mart_customer_lifetime_value` covers **4,975 customers** with
average lifetime revenue of **$2,383.72**.

**Why the snapshot matters:** customers change countries and emails. Without
type-2 history, last year's "UK revenue" silently becomes this year's "US
revenue" every time someone moves. The snapshot keeps every version with
`dbt_valid_from` / `dbt_valid_to` for point-in-time reporting.

## Tests — 25 total, all passing

**22 generic tests** (from `schema.yml` files): `unique` + `not_null` on every
primary key, `relationships` from order lines → customers/products,
`accepted_values` on currency and status.

**3 custom singular tests** (`tests/`) — the business rules a generic test
can't express:

1. `assert_no_negative_revenue` — revenue in the marts is never negative
   (a negative would mean a cleaning bug, never a real event).
2. `assert_daily_revenue_reconciles` — the daily mart ties out to the
   underlying order lines within $0.01 (catches filter/join drift before
   finance does).
3. `assert_no_future_orders` — no order dated after today (source clock bugs
   would corrupt freshness monitoring).

Column-level descriptions on all marts power `dbt docs` — run
`dbt docs generate && dbt docs serve` to browse lineage and documentation.

## Monitoring

`monitoring/check_pipeline.py` runs **after** `dbt build` and checks the *data*,
not just the job:

| Check | Rule | Current |
|---|---|---|
| Freshness | latest revenue date within 2 days of today | 1 day stale — PASS |
| Volume anomaly | latest day 0.5×–2× of trailing 28-day avg | 1.14× — PASS |
| Null-rate: revenue | must be 0 | 0 — PASS |
| Null-rate: customer email | under 15% | 7.8% — PASS |
| Orphan-order rate | under 5% | 0.5% — PASS |

Results append to the `pipeline_health` table (audit trail); any FAIL exits
non-zero so **CI fails**. In production, the FAIL branch would POST to Slack
(e.g. `requests.post(webhook, json={...})`) or send email via SES/SendGrid —
the check logic stays identical, only the notifier changes.

## CI

`.github/workflows/dbt-ci.yml` — on every push/PR: install → generate data →
`dbt build` (seeds, snapshot, models, all 25 tests) → `dbt docs generate` →
health monitor. A red build means the data or the models broke, caught before
merge.

## Run it locally

```bash
pip install -r requirements.txt
python generate_data.py          # create the raw extracts (+ data_manifest.json)
dbt build --profiles-dir . --project-dir ecommerce_analytics
python monitoring/check_pipeline.py
```

To browse docs: `dbt docs generate --profiles-dir . --project-dir ecommerce_analytics`
then `dbt docs serve --profiles-dir . --project-dir ecommerce_analytics`.

## Why DuckDB

DuckDB is an embedded analytical database — no server, no cloud bill, runs
anywhere. It executes the exact same dbt concepts as Snowflake/BigQuery
(models, seeds, snapshots, generic + singular tests, docs), so every skill
demonstrated here transfers 1:1 to a cloud warehouse. One dbt-duckdb note:
custom schemas become `<database>_<schema>` (e.g. `main_marts`); the monitor
accounts for this.

## Limitations (honest)

- FX rates are static and illustrative; production needs a daily rates table.
- The "keep highest price" rule for duplicate SKUs is a documented assumption —
  a real catalog would carry a version timestamp.
- Data is synthetic (seeded generator), so volume patterns lack real-world
  seasonality; thresholds are tuned to the generator, not to production traffic.
- Snapshots capture one point in time per run; true SCD history needs scheduled runs.
- The monitor's alerting is a documented pattern, not a live Slack integration.
